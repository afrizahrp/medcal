2A — Double-gate contradiction: CONFIRMED, with a clean fix
Traced through the actual installed better-auth@1.6.27 source, not assumption:

dispatch.mjs (dispatchAuthEndpoint): runBeforeHooks(...) (this is where @BeforeHook lands) is awaited at line 207, before endpoint(internalContext) (line 228, the real sign-up handler) is ever called. If a before-hook throws, that throw propagates out of dispatchAuthEndpoint directly — endpoint() never runs. So:

Reject case: @BeforeHook throws → request aborts → @BeforeCreate never fires. Fine.
Allow case (CUSTOMER_PORTAL + company-domain email — the actual bug-1 fix): @BeforeHook doesn't throw → execution proceeds into endpoint() → which internally calls databaseHooks.user.create.before, i.e. our unchanged, still-origin-blind @BeforeCreate in registration-gate.hook.ts → sees company domain, no whitelist entry → rejects.
So as currently implemented, bug 1 is not fixed — the rejection just moves from the first gate to the second. Confirmed exactly as you predicted.

Resolution — Option 1, and it's cleanly achievable: @thallesp/nestjs-better-auth's setupDatabaseHooks forwards ...args verbatim to our provider method. Better Auth's own with-hooks.mjs calls the database hook as toRun(actualData, context), where context = await getCurrentAuthContext() — an AsyncLocalStorage-backed accessor (@better-auth/core/context's endpointContextAsyncStorage) that resolves to the same internalContext object dispatchAuthEndpoint set up, including .headers. This means @BeforeCreate's handler can accept a second parameter and read context.headers.get("origin") directly — no store, no marker flag needed.

One nuance worth being upfront about: I also checked whether this ALS survives Better Auth's transaction wrapping (runWithTransaction, in transaction.mjs) — the original (rolled-back) report's stated failure mode. In this version, the transaction wrapper uses a separate AsyncLocalStorage instance (adapterAsyncStorage, holding only {adapter, pendingHooks, isTransactionActive}) from the one holding endpoint context (endpointContextAsyncStorage). Since they're independent ALS instances, nesting a .run() on one doesn't clear the other's active store within the same async chain — so structurally, getCurrentAuthContext() should still resolve correctly inside databaseHooks.user.create.before, even inside a transaction. This is strong static evidence, but I could not empirically prove it against a live Postgres in this sandbox (no DB available) — the end-to-end test you specified (customer@kalibrasimedika.co.id via portal.*, asserting a real User row gets created) is exactly the check that would catch it if my static reading is wrong, and I'll treat that test as load-bearing, not decorative, when Phase 3 resumes.

Chosen fix: make @BeforeCreate context-aware using the same resolveRegistrationContext + getRegistrationRejectionReasonForContext already built, reading context?.headers?.get("origin") from its second argument (falling back to fail-closed ORIGIN_NOT_ALLOWED if that argument is ever absent — e.g. any future direct-Prisma path that bypasses dispatchAuthEndpoint entirely). This removes the contradiction outright: both hooks agree, driven by one function.

Reverse case (staff → also wants a customer account under the same email): out of scope, by data model, not by omission. UserMembership is @@unique([userId, companyId]) — one role per user per company. There's no concept of a distinct "customer account" separate from the User row; "becoming a customer" would mean changing their role to CUSTOMER (losing staff access), which is a distinct feature decision, not something this registration-policy change should try to accommodate.
2C — Origin header reliability: traced hop-by-hop against the real infra files (not assumed)
Local dev: no reverse proxy — browser talks directly to both the Next.js app and the NestJS API on their own ports. Origin passes through unmodified.

Production (infra/nginx/*.conf.example, docker-compose.prod.yml) — with one important caveat: these are files whose own header comments call them "PROPOSED... NOT YET APPLIED"; I read the repo's plan for the live nginx config, not a fetch of the actual VPS config, since I have no access to it. With that caveat:

apps.kalibrasimedika.co.id's block proxies to the portal container and explicitly sets Host, X-Real-IP, X-Forwarded-For, X-Forwarded-Proto (plus Upgrade/Connection on the API block for WebSocket). Origin is never touched — nginx passes it through by default. Since the browser sets Origin itself (a forbidden header no application JS can override) based on the calling page's origin, and portal's API calls go straight from the browser to api.kalibrasimedika.co.id (confirmed by the compose file's own comment: "portal's session/API calls originate from the visitor's browser directly ... never from this container"), Origin should survive intact end-to-end.
Host cannot substitute for Origin at the API layer, and this isn't a style preference — it's structural. proxy.ts's Host-based routing operates on a different hop: the Host header the portal Next.js app receives when the browser requests pages from apps._/portal._. But requests to the API are a separate, direct browser→API fetch whose Host header is always api.kalibrasimedika.co.id — the API's own hostname — regardless of which frontend (apps.* or portal._) initiated the call. So Host carries zero information about Staff-vs-Customer intent at the point our hook runs; Origin is the only header that actually carries that signal to the API. This resolves 2C decisively in favor of keeping Origin, for a concrete structural reason, not a general assumption of interchangeability.
Unrelated but important finding surfaced by this trace: portal.kalibrasimedika.co.id has no DNS and no nginx config in the currently-approved production topology — apps.kalibrasimedika.co.id.conf.example's own comment states "portal._ and technician.* are not part of the current approved topology... no DNS exists for it," even though .env.production.example's TRUSTED_ORIGINS already lists it forward-looking. This doesn't affect the correctness of the design, but it means the CUSTOMER_PORTAL context can be built and tested in dev today, but can't be exercised against real production traffic until portal.* is actually provisioned — worth confirming this is already known/expected on your end, since it affects when this fix is actually observable in prod.
Conclusion for 2C: keep Origin as designed. No fallback to Host — Host doesn't carry the needed signal at all at the API hop.
