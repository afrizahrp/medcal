# Investigation: JobReferenceEquipmentUsed — Schema, Validation, Runtime Design

## Summary

The reference-equipment MASTER DATA side is genuinely solid: `EquipmentType` (types), `Equipment` (physical units — the prompt's "EquipmentUnit" is not the real model name, see below), `DeviceTypeEquipmentRequirement` (which types a DeviceType needs), `EquipmentCalibrationRecord` (append-only calibration history per unit), and `WorkOrderEquipment` (the actual units confirmed to accompany an ON_SITE WorkOrder) are all implemented end-to-end with Portal CRUD, validity derivation, and a confirm/lock gate before a WorkOrder can start. What's missing is exactly what the original audit found and remains true today: `JobReferenceEquipmentUsed` is 100% schema-only — it has no FK to `Equipment` at all (just free-text `equipmentName`/`brand`/`model`/`serialNumber` strings), and zero service/controller/module/UI code anywhere in `apps/` reads or writes it. It cannot even record "which unit" today, only a free-text description, so the model as it stands cannot fulfil the stated goal even if wired up — a schema change is required, not just a service layer.

The single most important finding for design purposes: because `WorkOrder.equipmentConfirmedAt` is a hard gate checked in `startWorkOrder()` immediately before `fanOutCalibrationJobs()` runs (`apps/api/src/modules/work-orders/work-orders.service.ts:475-514`), every `CalibrationJob` that will ever exist for an ON_SITE WorkOrder is created only *after* that WorkOrder's `WorkOrderEquipment` list is already locked in. This means job-level linking does not need a fresh "search all active units of type X" candidate flow (option analogous to Identity Correction's `findDeviceCandidates`) — it can simply be "pick N of the units already on this job's WorkOrder's `WorkOrderEquipment` list," which is both simpler to implement and semantically correct (a technician can't have brought a unit that wasn't confirmed to be brought).

## Step 1 — Live Schema & Master-Data Runtime

All models read directly from `packages\db\prisma\schema.prisma`.

**Naming correction to the brief**: there is no `EquipmentUnit` model. The physical-unit master is called `Equipment` (Portal route `management/equipment-units`, hence the terminology mismatch). `EquipmentType` is the type/category master (Portal route `management/equipment-types`). Requirements live in `DeviceTypeEquipmentRequirement` (Portal route `management/equipment-requirements`).

**`EquipmentType`** (schema.prisma:1059-1073) — global master, no companyId: `id, code (unique), name, description?, category?, isActive`. Relations: `deviceRequirements DeviceTypeEquipmentRequirement[]`, `equipment Equipment[]`.

**`Equipment`** (schema.prisma:1084-1107) — company-scoped physical unit: `id, companyId, equipmentTypeId, code, brand?, model?, serialNumber?, isActive, notes?`. `@@unique([companyId, code])`. Relations: `calibrationRecords EquipmentCalibrationRecord[]`, `workOrderSelections WorkOrderEquipment[]`. Comment explicitly says validity is DERIVED, never stored on this row.

**`EquipmentCalibrationRecord`** (schema.prisma:1128-1156) — append-only calibration event: `id, companyId, equipmentId, calibrationDate (Date), validFrom (Date, nullable), validUntil (Date, required), certificateNumber?, provider?, result?, remarks?, acceptedForUse (Boolean, default false), acceptedByUserId?, acceptedAt?, acceptanceNotes?, status (DRAFT|CONFIRMED, default DRAFT)`. Confirms the brief's assumption directly: `validFrom`/`validUntil` is the exact field pair, both `@db.Date` (date-only, no time component). `acceptedForUse` is a separate MEDCAL acceptance decision, NOT auto-derived from `result` — a unit can have `result` = pass but `acceptedForUse` = false, or vice versa; today's `resolveCalibrationValidity` (below) does not even look at `acceptedForUse`, only `status === "CONFIRMED"` + the date window. That is a real gap worth flagging (see Open Questions).

**`DeviceTypeEquipmentRequirement`** (schema.prisma:1164-1187) — master config only: `deviceTypeId, equipmentTypeId, notes?, sortOrder`. Comment states explicitly: "The required set for a CalibrationJob is derived at read time from `job.device.deviceTypeId`, never copied onto WorkOrder / CalibrationJob."

**`WorkOrderEquipment`** (schema.prisma:1696-1721) — actual units selected for an ON_SITE WorkOrder: `id, companyId, workOrderId, equipmentId, equipmentTypeId (snapshot), sortOrder, notes?`. `@@unique([workOrderId, equipmentId])`.

**`JobReferenceEquipmentUsed`** (schema.prisma:1908-1921) — the model in question, verbatim:
```prisma
model JobReferenceEquipmentUsed {
  id               String   @id @default(cuid())
  calibrationJobId String
  equipmentName    String
  brand            String?
  model            String?
  serialNumber     String?
  createdAt        DateTime @default(now())
  updatedAt        DateTime @updatedAt

  calibrationJob CalibrationJob @relation(fields: [calibrationJobId], references: [id], onDelete: Cascade)

  @@index([calibrationJobId])
}
```
No `equipmentId` FK to `Equipment`, no `companyId`, no calibration-record reference, no timestamp-of-use field. It is a free-text description table, structurally incapable of the traceability goal ("this job used EQU-000003, certificate valid at time of use") without a schema migration adding at minimum `equipmentId String` (FK to `Equipment`) and ideally `equipmentCalibrationRecordId String?` (FK to the specific `EquipmentCalibrationRecord` snapshot that was valid at use time, mirroring how `WorkOrderEquipment.equipmentTypeId` is a snapshot).

**`CalibrationJob`** (schema.prisma:1788-1878) carries `referenceEquipmentUsed JobReferenceEquipmentUsed[]` (line 1865) confirming the relation exists but, per the grep in Step 1.4 below, is never read/written anywhere in application code.

**Validity check — confirmed via `apps/api/src/modules/equipment-calibration-records/calibration-validity.ts`**: a pure, already-implemented, already-unit-tested function `resolveCalibrationValidity(records, asOf): { status: "VALID"|"EXPIRED"|"NOT_YET_VALID"|"NO_RECORD", recordId, validUntil }`. It filters to `status === "CONFIRMED"` records, computes interval start as `validFrom ?? calibrationDate`, and checks `intervalStart <= asOf <= validUntil`. The file's own header comment says: "deliberately NOT wired to CalibrationJob / WorkOrder — the authoritative 'equipment use date' for job-level validation is an open business decision." This is exactly the reusable piece the brief asked about — it exists, is correct, and needs no reimplementation, only a caller.

**`Equipment.isActive` vs. calibration validity — confirmed independent**, exactly as the brief hypothesized. `validateEquipmentSelection` in `apps/api/src/modules/work-orders/work-order-equipment.ts:174-250` checks them as two entirely separate conditions: `!unit.isActive` throws a blocking `EQUIPMENT_INACTIVE` error; a non-`VALID` `resolveCalibrationValidity` result is pushed as a non-blocking **warning** (`EQUIPMENT_CALIBRATION_NOT_VALID`), not a throw. So today's precedent treats "Aktif but certificate expired" as merely advisory, while "Nonaktif" (regardless of certificate) is hard-blocked. A unit can indeed be Aktif with an expired certificate (warned, not blocked) or, in principle, Nonaktif with a currently-valid certificate (blocked regardless of certificate state).

**Existing equipment-adjacent services** (`apps/api/src/modules/equipment/`, `apps/api/src/modules/equipment-calibration-records/`):
- `EquipmentService` (`equipment.service.ts`): `create`, `findAll`, `findOne`, `update`, `remove` — plain CRUD, no "give me valid units of type X" query method.
- `EquipmentCalibrationRecordsService` (`equipment-calibration-records.service.ts`): CRUD plus `getValidity(companyId, equipmentId, asOf): Promise<CalibrationValidityResult>` (line 139) — a ready-made per-unit validity lookup a new linking feature could call directly instead of re-querying `calibrationRecords` and re-running `resolveCalibrationValidity` itself.
- The actual "find active units of type X with derived validity, batched across types" logic lives in `apps/api/src/modules/work-orders/work-order-equipment.ts` as `loadEquipmentCandidates()` (lines 113-149) and `validateEquipmentSelection()` (lines 174-250) — WorkOrder-scoped, but both are pure/reusable functions taking a `Db` pick-type, not bound to WorkOrder internals, so they generalize cleanly to a job-level caller.

**Zero runtime confirmation**: `Grep` for `JobReferenceEquipmentUsed|referenceEquipmentUsed` across `apps/` returns no matches outside `schema.prisma`'s own type generation — no controller, service, module, DTO, or UI component anywhere touches it. This matches and reconfirms the original audit's "schema-only, zero runtime" finding; nothing has changed on this specific table.

## Step 2 — Where This Fits in the Job Lifecycle

**`resolveJobDeviceTypeId`** (private method, `apps/api/src/modules/calibration-jobs/calibration-jobs.service.ts:292-298`):
```ts
private resolveJobDeviceTypeId(job: CalibrationJobDetail): string | null {
  return (
    job.calibrationRequestItem?.deviceTypeId ??
    job.purchaseOrderItem?.quotationItem?.requestItem?.deviceTypeId ??
    null
  );
}
```
It resolves a single DeviceType for one job (preferring the direct `calibrationRequestItem` link, falling back through the PO-item chain). It is used both for device-candidate search (`findDeviceCandidates`, line 377) and Identity Correction device-type-match validation (`validateDeviceForJob`, line 306).

**`resolveRequiredEquipmentTypes`** (`apps/api/src/modules/work-orders/work-order-equipment.ts:80-110`) already exists, but is WorkOrder-scoped by signature: it takes `deviceTypeIds: string[]` (plural, aggregated across every item on a WorkOrder) and returns a deduplicated, ordered `ProposedEquipmentType[]`. There is no `resolveRequiredEquipmentTypesForJob` — but none is needed as a new implementation: the existing function is a pure function over an array of DeviceType ids, so calling it with a **one-element array** (`[resolveJobDeviceTypeId(job)]`) trivially derives the required EquipmentTypes for a single job, with the same dedupe/ordering logic already tested. This confirms the brief's suspicion: the WorkOrder-level function is reusable at job granularity essentially unchanged; it was never job-scoped because until now nothing needed a single-job view of it.

**Investigating options (a)/(b)/(c):**

- **(b) is ruled out as currently viable**: `Grep` for `MeasurementResult` across `apps/` returns **zero matches** outside `schema.prisma`. The model (`payloadJson Json`, `summaryJson Json?`) has no service, no controller, no UI — it is confirmed untyped-blob-with-no-runtime, exactly as the brief suspected. Tying reference-equipment recording to "when measurements are recorded" would mean building on a foundation that doesn't exist yet, so it isn't a near-term option.

- **(c) is the best-supported reading of the code as it stands.** `WorkOrder.equipmentConfirmedAt` is a hard-gated field: `startWorkOrder()` (`apps/api/src/modules/work-orders/work-orders.service.ts:475-514`) throws `WORK_ORDER_EQUIPMENT_NOT_CONFIRMED` if an ON_SITE WorkOrder has unconfirmed equipment and any requirement or existing selection exists, and this check runs immediately before `fanOutCalibrationJobs(tx, existing)` in the same function (same status transition PLANNED/ASSIGNED → IN_PROGRESS). Consequence: **every `CalibrationJob` row for an ON_SITE WorkOrder is created only after that WorkOrder's `WorkOrderEquipment` list already exists and is locked.** So "which units are available for this WO's jobs" is already answered by `WorkOrderEquipment` by construction — a job-level linking UI does not need a fresh device-candidate-style search across all `Equipment`; it can and should offer a picker scoped to `WorkOrderEquipment` rows for `job.workOrderId` (optionally further filtered to the EquipmentTypes required by that job's own resolved DeviceType, using `resolveRequiredEquipmentTypes([deviceTypeId])` against the WO's already-selected list). This turns "job-level linking" into an assignment/selection problem, not a search problem — cheaper to build and matches the confirmed fan-out design's spirit (each job independently draws from a shared, already-vetted WorkOrder-level pool).

- **(a) is where the recording action itself should live**, but its data source is (c). The technician already goes through an on-site, job-scoped flow (Identity Correction: `apps/tech-pwa/src/app/jobs/[id]/identity-correction/*`) recording "what device is this." "What reference equipment did I use to calibrate it" is a natural adjacent step in the same on-site session — the technician is standing there with the units in hand and can identify by `Equipment.code`/serial far more reliably than anyone reconstructing it later. Note tech-pwa currently has **zero equipment awareness at all** — `Grep` for `equipment` (case-insensitive) across `apps/tech-pwa/src` returns no matches. Only the Portal (`apps/portal/src/app/management/work-orders/work-order-equipment-section.tsx`) currently displays `WorkOrderEquipment`. So building this feature also requires exposing (at minimum, read-only) the WO's confirmed equipment list inside tech-pwa for the first time — there is no existing tech-pwa equipment UI to extend, only the Portal pattern to mirror.

## Step 3 — Design Options

**1. Endpoint/data shape.** Job ↔ Equipment should be many-to-many via a join-style table (schema change required: add `equipmentId` FK to `JobReferenceEquipmentUsed`, or introduce a properly named replacement, e.g. `JobReferenceEquipmentUsed { calibrationJobId, equipmentId, equipmentCalibrationRecordId? }`, dropping the free-text fields in favor of the FK — a Bed Side Monitor job may use 3 different reference units per the Requirements example, so no `@@unique` beyond `[calibrationJobId, equipmentId]`). For the endpoint shape, the codebase has one clear, working precedent — `WorkOrderEquipment`'s **full-set replace pattern**: `PUT :id/equipment` (`replaceEquipment`, full array in, full array out — `apps/api/src/modules/work-orders/work-orders.controller.ts:101-116`), plus a separate `POST :id/equipment/confirm` lock step and `PATCH :id/equipment/order` for reordering. Recommend mirroring this exactly at the job level: `PUT /calibration-jobs/:id/reference-equipment-used` taking `{ equipmentIds: string[] }` (or `{ items: [{ equipmentId, notes? }] }` if per-line notes are wanted) and replacing the full set transactionally — simpler than an add/remove pair, consistent with the one existing similar feature, and appropriate given the expected small N (a handful of units per job) and the fact the set is re-derivable/re-editable up until some job-status gate (see below), not an append-only audit log.

**2. Validation.** Reuse, don't reimplement:
   - **Existence + company scope**: unit must belong to `companyId` (mirrors `EQUIPMENT_NOT_FOUND`).
   - **Active check (blocking)**: `Equipment.isActive` must be true — reuse the `EQUIPMENT_INACTIVE` blocking pattern from `validateEquipmentSelection`.
   - **Type check (blocking, optional)**: if the UI scopes selection to `resolveRequiredEquipmentTypes([jobDeviceTypeId])`, this is naturally enforced by the picker; if the endpoint accepts arbitrary equipment ids it should still validate `equipmentTypeId` is one of the job's required types, mirroring `EQUIPMENT_TYPE_MISMATCH`.
   - **Calibration validity — recommend the job's actual execution date (`CalibrationJob.startedAt`), not "now", as the `asOf` value**, because the record is meant to answer "was the certificate valid at the moment this job actually used the unit," and `startedAt` is the field that captures that moment (falling back to "now" only if `startedAt` is still null, i.e. recording is attempted before work started — arguably that itself should be disallowed, see Open Questions). This is a deliberate but small divergence from the brief's default suggestion of "now."
   - **Blocking vs. warning — recommend diverging from `WorkOrderEquipment`'s warning-only precedent.** At WorkOrder equipment-confirmation time the unit hasn't been used yet (planning stage — a warning is enough to flag "double check this before you leave"). At job-level recording time the technician is asserting **"I actually used this unit to produce these results"** — a job with a provably expired certificate at use time is a compliance/traceability problem, not a planning nicety. Recommend making `EQUIPMENT_CALIBRATION_NOT_VALID` a **blocking** `BadRequestException` at job-level recording (distinct code, e.g. `JOB_REFERENCE_EQUIPMENT_CALIBRATION_EXPIRED`, message: `"Equipment {code} calibration was not valid ({status}) on {asOf date}"`), unless the business wants an override path (e.g. TECHNICIAN_MANAGER can force-accept with a reason, similar to how `acceptedForUse` already lets MEDCAL override a lab `result`). This is a real behavior change vs. the existing precedent and should be called out to the user, not assumed silently.

**3. Portal vs. tech-pwa.** Following the Identity Correction precedent exactly (`submitIdentityCorrection` = TECHNICIAN + TECHNICIAN_MANAGER; `decideIdentityCorrection`/`approveIdentity` = TECHNICIAN_MANAGER-only, per `packages/db/prisma/seed-role-permissions.ts:147-160`): the technician on-site is the only actor who actually knows which physical unit they grabbed, so **recording** the used-equipment list belongs in **tech-pwa**, scoped to the job detail flow (new step alongside/after Identity Correction, before or alongside the eventual measurement-recording flow once that exists). **Portal** should get a read-only display (job detail / QA review context) so TECHNICIAN_MANAGER and QA reviewers can see what was used — no separate "approve equipment used" decision is evident from the brief's requirements, so Portal likely needs no write action here, unlike Identity Correction which has a real approval gate (AKD/AKL regulatory consequence). Building the tech-pwa picker requires first surfacing `WorkOrderEquipment` (read-only) in tech-pwa, which does not exist there today.

**4. RBAC.** Reuse the existing `calibrationJob` resource with a new action, exactly the established convention (`escalateIdentity`, `approveIdentity`, `submitIdentityCorrection`, `decideIdentityCorrection` are all actions on `calibrationJob`, not separate resources — confirmed via `@RequirePermission("calibrationJob", ...)` in `apps/api/src/modules/calibration-jobs/calibration-jobs.controller.ts` and the WorkOrder-equipment endpoints similarly reusing `@RequirePermission("workOrder", "update")` rather than a new `workOrderEquipment` resource). Recommend a single new action, e.g. `recordReferenceEquipmentUsed`, granted to both `TECHNICIAN` and `TECHNICIAN_MANAGER` (mirroring `submitIdentityCorrection`'s grant pattern), with `calibrationJob:read` sufficient for Portal's read-only display — no new resource needed.

## Open Questions for User Confirmation

1. **Schema change is mandatory, not optional.** `JobReferenceEquipmentUsed` as it exists today has no `equipmentId` FK — it cannot record "which physical unit" at all, only free-text strings. Confirm whether to add `equipmentId` (and optionally `equipmentCalibrationRecordId` as a validity snapshot) to the existing table, or replace it with a differently-shaped join table. This is a real migration, not a service-layer-only change.
2. **Should the validity check use `job.startedAt` or "now" (submission time) as `asOf`?** The report recommends `startedAt` as more correct; confirm this is the intended semantic, and confirm what happens if a technician tries to record equipment before the job has `startedAt` set.
3. **Should an expired-certificate unit be a hard block or a warning at job level?** The report recommends blocking (diverging from `WorkOrderEquipment`'s warning-only precedent) given the compliance stakes of asserting actual use; confirm this is the intended business behavior, and if a manager override/force-accept path is wanted for edge cases (equipment recalibrated on paper but system not yet updated, etc.).
4. **Should `acceptedForUse` factor into validity at all?** Today `resolveCalibrationValidity` ignores it entirely, checking only `status === "CONFIRMED"` + the date window. A record could be date-valid but never marked `acceptedForUse`. Confirm whether job-level (or even WorkOrderEquipment-level) validity should also require `acceptedForUse === true`.
5. **Does Portal need any write/approval action here, or is read-only sufficient?** Unlike Identity Correction's AKD/AKL regulatory gate, no approval workflow is evident from the requirements as stated — confirm there is no QA/manager sign-off needed on "which reference equipment was used" before it's treated as final (e.g. at Certificate issuance time).
6. **Should tech-pwa gain a general "confirmed equipment for this WorkOrder" read-only view** (currently absent) as a prerequisite, or should the job-level picker fetch that data inline without a dedicated screen?
