## 1. Migration files generated

### 1.1 `20260908025128_add_measurement_result_file_owner_type/migration.sql`

```sql
-- AlterEnum
ALTER TYPE "FileOwnerType" ADD VALUE 'MEASUREMENT_RESULT';
```

**Why its own migration.** Per design §3.6. Repo-precedent check: enum-value additions in this repo
appear **both** combined with other DDL (`20260904071251` added `FileOwnerType.IDENTITY_CORRECTION`
alongside `CreateTable`; `20260829050000` added `FileOwnerType.EQUIPMENT_CALIBRATION` alongside
`AlterTable`) **and** standalone (`20260901120000` = one `ALTER TYPE "DocumentType" ADD VALUE`;
`20260902022658` = one `ALTER TYPE "MembershipRole" ADD VALUE`). The standalone form is the safer
one under Postgres' "new enum value cannot be used in the same transaction that added it" rule and is
an existing, blessed pattern here — so this stage uses it. Generated by
`prisma migrate dev --create-only`; **not hand-edited.** Applied with `prisma migrate dev`.

### 1.2 `20260908025400_restructure_measurement_result_and_add_test_point/migration.sql`

Full file is in the repo. Structure:

- `CREATE TYPE "MeasurementDirection" AS ENUM ('NONE', 'UP', 'DOWN')`
- `CREATE TYPE "MeasurementEntryKind" AS ENUM ('DIRECT_READING', 'LOGGER_SUMMARY')`
- `ALTER TABLE "CalibrationJob" ADD COLUMN "currentAttempt" INTEGER NOT NULL DEFAULT 1`
- `ALTER TABLE "MeasurementResult" DROP COLUMN "payloadJson", DROP COLUMN "summaryJson", ADD COLUMN …`
  (19 new columns incl. `attemptNumber`/`replicateIndex` `NOT NULL` with no default — safe, 0 rows;
  `deviceCalibrationParameterId TEXT NOT NULL` — closes gap F2; `direction … NOT NULL DEFAULT 'NONE'`;
  `entryKind … NOT NULL DEFAULT 'DIRECT_READING'`; `updatedAt TIMESTAMP(3) NOT NULL`)
- `CREATE TABLE "CalibrationTestPoint" (…)` + its pk
- Indexes: `CalibrationTestPoint` — `@@index(deviceCalibrationParameterId)`,
  `@@unique(deviceCalibrationParameterId, sequence)`, `@@unique(deviceCalibrationParameterId, settingLabel)`
- Indexes: `MeasurementResult` — `(calibrationJobId, attemptNumber)`, `(deviceCalibrationParameterId)`,
  `(calibrationTestPointId)`, `(companyId)`, `(attachmentFileObjectId)`
  (`@@index([calibrationJobId])` already existed and is retained)
- **Natural-key unique index — HAND-EDITED:**

  ```sql
  CREATE UNIQUE INDEX "MeasurementResult_calibrationJobId_deviceCalibrationParamet_key"
    ON "MeasurementResult"("calibrationJobId", "deviceCalibrationParameterId",
      "calibrationTestPointId", "replicateIndex", "attemptNumber", "direction")
    NULLS NOT DISTINCT;
  ```

  The ` NULLS NOT DISTINCT` suffix is the only hand-edit to this line — added because
  `calibrationTestPointId` is nullable (Pattern A / note-only) and default Postgres NULL-distinctness
  would let a duplicate `(job, param, NULL, 1, 1, NONE)` slip through. Prisma's `@@unique` cannot
  express this. The `name: "measurement_natural_key"` argument on the `@@unique` block is the
  Prisma-client compound-key alias only, **not** the DB identifier, so the generated index name is
  kept and there is no drift. **This is the first use of `NULLS NOT DISTINCT` in the repo** — no
  prior precedent existed to follow; the hand-edit convention followed is the same `-- HAND-EDITED`
  comment style used for the CHECK constraints below.

- Foreign keys: `CalibrationTestPoint.deviceCalibrationParameterId` → `DeviceCalibrationParameter` (Cascade);
  `MeasurementResult` → `DeviceCalibrationParameter` (Restrict), `CalibrationTestPoint` (Restrict),
  `Uom` (SetNull), `User` recordedBy (SetNull), `FileObject` attachment (SetNull).
  (`calibrationJob` FK Cascade already existed and is retained.)
- **CHECK constraints — HAND-EDITED** (design §3.6; Prisma cannot model CHECK — same raw-SQL pattern
  as `DeviceCalibrationParameter_decimalPlaces_range` and `CalibrationRequestItem_qty_positive`):

  ```sql
  ALTER TABLE "MeasurementResult"
    ADD CONSTRAINT "MeasurementResult_replicateIndex_positive" CHECK ("replicateIndex" >= 1);
  ALTER TABLE "MeasurementResult"
    ADD CONSTRAINT "MeasurementResult_attemptNumber_positive"  CHECK ("attemptNumber"  >= 1);
  ALTER TABLE "CalibrationTestPoint"
    ADD CONSTRAINT "CalibrationTestPoint_sequence_positive"    CHECK ("sequence"       >= 1);
  ```

**Generation method.** `prisma migrate dev --create-only` refuses to run non-interactively when it
has a datasource warning to acknowledge (the "a unique constraint … will be added" notice), so the
SQL was produced with
`prisma migrate diff --from-url "$DATABASE_URL" --to-schema-datamodel prisma/schema.prisma --script`
(DB was already at `20260908025128`, so the diff is exactly this stage's delta), written into the
migration folder, then hand-edited, then applied with `prisma migrate deploy`. `migrate deploy`
recorded it in `_prisma_migrations` normally.
