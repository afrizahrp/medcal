## 2. What was implemented

1. **Fixture source of truth** — `source-rows.ts` (56 rows, verbatim names/qty, self-checking that it sums to exactly 406) and `device-type-mapping.ts` (tier + `DeviceType.code` per row, self-checking against the locked tier totals: EXACT 5/156, ALIAS 4/45, REPRESENTATIVE 10/64, SYNTHETIC 37/141).
2. **Synthetic master data** — one idempotent seed script creates 37 `TRIAL_MH_*` DeviceTypes across 4 new categories (Ophthalmology, Medical Imaging, Physiotherapy, Measurement Instruments) plus 5 reused existing categories (Resuscitation, Suction & Fluid, Respiratory & Oxygen, Patient Care, Laboratory & Diagnostic). Every DeviceType gets exactly 2 `DeviceCalibrationParameter` rows (Pattern A, default `entryStyle=DIRECT_REPLICATES`), reusing two existing, global `DeviceCapabilityItem` rows (Environmental Conditions/Room Temperature, Electrical Safety/Protective Earth Resistance) that are already present on nearly every real LK worksheet — no new `DeviceCapability`/`DeviceCapabilityItem` was created, and no existing master-data row was edited.
3. **406-job generation** — one real `Customer` ("RS Minto Hardjo (Trial)") under the existing `Company` "PKM", one `CalibrationRequest` (56 items, Σqty=406) created through `CalibrationRequestsService.create()` (functionally identical to `CalibrationRequestImportService.confirm()`, which is a thin passthrough to the same method — called directly for a stable typed surface; the real `preview()` endpoint is still exercised first, read-only, as a cross-check), submitted, quoted, approved, converted to a `PurchaseOrder`, approved, converted to the one `WorkOrder`, assigned to a 4-technician pool, and started — the real `fanOutCalibrationJobs()` produced exactly 406 `CalibrationJob` rows.
4. **State distribution** — a deterministic (no RNG) planner assigns each non-Ambulatory-ECG job a target status matching the ~60/15/10/4/11% split, then the script drives every transition through the real service methods (`start()`, `submitForReview()`, `decideQualityReview()`, `resumeAfterRework()` semantics via the REWORK terminal path, `complete()`), filling real `MeasurementResult` rows against each job's frozen `JobCalibrationTestPoint` snapshot (Pattern A and Pattern B both handled generically) to satisfy the real completeness gate. A small deliberate set of readings are pushed outside the parameter's/point's own resolved tolerance bounds.
5. **Identity Corrections** — 28 total, spread across 24 distinct device types and unit ordinals 1–6 (never clustered), submitted and decided through the real `submitIdentityCorrection()`/`decideIdentityCorrection()` methods.
6. **Reset/reseed** — `reset.ts` deletes the trial transaction chain in dependency order and deactivates every manifested synthetic master-data row; `seed.ts` refuses to run again while a manifest or the trial Customer already exists.

## 5. Actual Identity Correction distribution

28 total: **22 PENDING_REVIEW, 4 APPROVED, 2 REJECTED** — matching the ~22/~4/~2 target exactly.

Spread across **24 distinct device types** (far exceeding the "at least 5–6" requirement), including real EXACT-tier (Centrifuge, CPAP, Infusion Pump, Syringe Pump), ALIAS-tier (Electrocardiographs, Nebulizer Compressor, Pulse Oximeters), REPRESENTATIVE-tier (Sterillizer, Sphygmomanometers), and 14 different `TRIAL_MH_*` synthetic types. `unitOrdinal` positions observed: `1, 2, 1, 2, 3, 2, 1, 1, 3, 3, 4, 1, 1, 2, 1, 6, 2, 2, 6, 2, 2, 3, 1, 5, 1, 3, 5, 1` — genuinely scattered (positions 1 through 6), not clustered on unit #1.

A pending correction was only ever left open on a job whose own target status stops at `IN_PROGRESS` (never on a job destined for `SUBMITTED`+), respecting `IDENTITY_LOCKED_JOB_STATUSES` (`SUBMITTED`, `ACCEPTED_BY_QA`) in `calibration-jobs.service.ts` — a pending BA would otherwise make that job's own later `submitForReview()` throw `IDENTITY_CORRECTION_UNRESOLVED`. Decided (APPROVED/REJECTED) corrections were drawn from jobs headed to SUBMITTED/REWORK/ACCEPTED_BY_QA, resolved before that job's own measurement/submit sequence ran.

## 10. Deviations from the approved plan

1. **Script relocation (mechanical, instructed).** `seed-trial-minto-hardjo.ts`/`reset-trial-minto-hardjo.ts` moved from `packages/db/scripts/` (as the plan specified) to `apps/api/scripts/trial-minto-hardjo/{seed,reset}.ts`, because `packages/db` must never import from `apps/api` (backwards dependency direction) and the real service classes this task must call (`CalibrationRequestsService`, `QuotationsService`, `PurchaseOrdersService`, `WorkOrdersService`, `CalibrationJobsService`, `MeasurementResultsService`) only exist inside `apps/api/src/modules/**`. The fixture data files and the synthetic-master seed script stayed exactly where the plan put them, under `packages/db/`. This is a mechanical relocation, not a scope or architecture change.

2. **Single serviceMode — the plan's own C.4/C.7 are in tension, resolved in favor of C.4.** Confirmed at the code level (`work-orders.service.ts` — `serviceMode: request.serviceMode` copied at `WorkOrder.create()` and immutable afterwards; `quotations.service.ts` — at most one `Quotation` per `CalibrationRequest`, confirmed by the audit's own §B.3) that one `CalibrationRequest`/one `WorkOrder` (which the plan itself locks in C.4 step 7, "the trial's only WorkOrder") can only ever have **one** `serviceMode`. This dataset uses `SEND_TO_LAB` throughout (richer real flow — exercises the Kontrol Alat gate). Two consequences, both genuine architectural blockers, not resolved by inventing a second, out-of-406 WorkOrder (which decision 1, "no manufactured jobs", forbids):
   - The plan's Tech-PWA scenario table row "SEND_TO_LAB vs ON_SITE, one of each" cannot be satisfied from the real 406 — there is no ON_SITE job in this dataset. Dropped, not worked around.
   - The "reference-equipment approval pending" scenario is **also** unreachable for the identical root cause: confirmed at runtime (`job-reference-equipment.ts` `validateJobReferenceEquipmentSelection`, and `work-orders.service.ts` `confirmEquipment()` throwing `EQUIPMENT_NOT_APPLICABLE_FOR_SEND_TO_LAB` for any non-ON_SITE WorkOrder) that reference-equipment selection is only reachable on an ON_SITE WorkOrder. Dropped from the Tech-PWA list; two other real scenarios (submitted-awaiting-review, fully-completed) substituted to keep the list at 14.

3. **Representative-tier arithmetic correction.** The plan's prose states the REPRESENTATIVE tier is "10 items / 66 units", but summing the plan's own per-row quantities for exactly the 10 named items (Audiometri 2, BSC 2, Medical Frezer 1, EKG 20, Parafin Bath 1, Photo Therapy 5, HENC Ambubag 2, Resuscitator/Neo Puff 1, Sterilisator Basah 2, Tensimeter Analog 28) totals **64**, not 66. With EXACT (156) and ALIAS (45) fixed by the real per-row quantities, and total fixed at 406, the SYNTHETIC tier is correspondingly 141 (not 139) once Microscope's 2 units are added to it per the plan's own explicit instruction. This is a one-line arithmetic fix to the planning document's prose, not a change to any per-row quantity; the real numbers (406 total, 156/45/64/141 by tier) are what `device-type-mapping.ts` encodes and self-checks.

4. **Category-count ambiguity, resolved toward semantic plausibility.** The plan says synthetic DeviceTypes get "the closest fitting existing DeviceCategory, with one new category only if genuinely nothing fits" (singular "one"). Four genuinely distinct, uncovered domains were found (ophthalmology, general medical imaging, physiotherapy, general weighing/measurement instruments) — forcing all of them into a single new bucket, or into an existing but semantically wrong category (e.g. an ophthalmic biometer under "Audiology & Physiological Testing"), would have violated the plan's own "semantically plausible" requirement more than adding categories violates "minimize new categories". Four new categories were created instead of one; this is flagged explicitly as an interpretation of an ambiguous instruction, not a silent redesign.

5. **A real implementation bug was found and fixed during validation**, not merely designed around: the first seed run's measurement filler used a flat parameter-level tolerance fallback (0–100) for Pattern-B (`CalibrationTestPoint`) parameters whose bounds are only resolvable from the per-point frozen snapshot (`JobCalibrationTestPoint.toleranceMin/Max`, itself resolved from a "± X%" free-text note against that point's own `settingValue`) — producing 309 unintended out-of-tolerance readings instead of "a small deliberate handful". Fixed in `lib.ts`'s `fillJobMeasurements` to read the frozen per-point bounds directly; after the fix and a reset+reseed, exactly 12 out-of-tolerance readings remain, all deliberate and verified against each row's own resolved bounds.

**Everything else follows the approved plan with no scope deviation**: 406 (not 409) real jobs from one real WorkOrder; real service-method calls only (no raw status writes anywhere in the transaction chain); the exact tier-priority mapping order; no new `DeviceTypeAlias`; `akdAklApprovalStatus` left `NOT_REQUIRED` on all 406 jobs; `isActive=false` as the sole master-data isolation mechanism (no schema change); no production business-logic/RBAC/Portal/Tech-PWA UI change; no bulk-approval feature; no AKD/AKL UI; no environment/production safety gate of any kind.
